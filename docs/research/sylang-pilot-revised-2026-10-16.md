# Sylang pretrained-model pilot, revised (2026-10-16)

A comparison of the evidence assessment of 2026-10-16 (`sylang-evidence-assessment-and-plan-2026-10-16.md`, "the assessment") with the second-opinion plan "Sylang: a fast, evidence-led development plan" (16 October 2026, "the second opinion"), and one revised, staged pilot that replaces the assessment's §3–§4. Prepared on the development server. **Nothing has been rented, downloaded from a model hub, or spent; Git history is unchanged; no output format has been adopted.** The owner's priority order applies throughout: machine efficiency and an improved Sylang M first, readable Prime later.

Sections: 0 plain-English summary · 1 where the two plans agree, where they differ and why · 2 the seven concerns, answered with mechanisms · 3 the revised pilot (stages, cells, decision rules, budget) · 4 provider choice · 5 owner setup steps · 6 what is prepared on the server · 7 the next approval.

---

## 0. The summary in plain English

The two plans want the same experiment: fine-tune one small open model four ways on identical synthetic cases (compact Sylang codes, an improved-M candidate, controlled English, compact JSON), grade every output with one deterministic grader, count whole requests with the model's own tokenizer, and judge on correct work per dollar and per second. They differ chiefly on four things, *what the first test case is*, *how much to run before looking*, *how to read the result* and *where to run it*, and on two smaller ones, how much of M to change at once and whether to quantise the base model (§1.2).

What this revision does, in one sentence each:

- **Keeps the study's record schema and adds one second task** (relationship lookup) rather than switching to a GBG task-status schema now; the GBG schema is the integration stage's job, after the format question has an answer.
- **Stages the sweep**: profile the whole cycle on the GPU first (stage A), then one matched four-arm comparison with one seed and one answer format (stage B, exploratory by rule), then three seeds and the answer-format factor (stage C), with the decision rule written before any run.
- **Replaces "tied" with a non-inferiority rule** (δ = 3 points, 90% cluster bootstrap over seeds then items), under which an interval that reaches both acceptable and unacceptable differences is *inconclusive*, never a pass.
- **Treats the improved-M candidate as one reversible change** (grouping records by subject), chosen because the pilot data have repeated subjects, where grouping has the largest measured token gain (−20% to −29% at K = 16) and is the only idea whose grammar change needs a model test; the dictionary costs tokens on short identifiers, spaces instead of tabs save 6% and macro codes 1%, neither needing a GPU.
- **Makes every runtime and cost figure a measurement**: the package profiles load, training, generation, checkpointing and upload on the actual GPU and projects the later stages from that, with failed runs and retries inside a 1.5× contingency and a US$100 all-in ceiling.
- **Counts the whole request**: legend (system message), instruction, records, chat-template overhead, output, the retry, parsing and conversion wall-clock, under a cached and an uncached convention side by side, converted to latency and cost per correct task.
- **Recommends a free-credit provider first**: Lightning AI's L4 Studio (5 signup credits cover stages A and B; 25 more after adding a card cover stage C), with Thunder Compute's RTX A6000 at US$0.35 per hour as the paid fallback; Runpod only on an actual quote.

**Status.** The reproducible package (`experiments/pretrained_pilot/`) is written and smoke-tested on the CPU server with a tiny (about 10 M parameters, two layers) randomly initialised model of the Qwen 3 architecture class and the real Qwen 3 tokenizer (section 6 has the exact state). **The next approval needed** is in section 7: stage A + B on Lightning's free credits (no payment method), with the Qwen3-0.6B weights downloaded on the rented machine only.

## 1. Where the two plans agree, where they differ, and why

### 1.1 Agreement (no change needed)

Freeze a contract before training; test the evaluator with deliberately corrupted outputs; one JSON target and one grader for every rendering; split by underlying case and hold out wordings, feature combinations and a length band; audit complete requests with the unchanged tokenizer; profile before committing GPU money; report every seed, failure and retry; distinguish equal-items from equal-compute comparisons; no custom vocabulary and no Prime training in this pilot; GBG integration later, behind a flag that is off by default and only after the gate passes. The second opinion's reading of the evidence (two of five seeds learned for both English and Sylang; 93/96 and 92/96 on the handoff demo; 10,275 vs 14,927 process tokens, the v3 demo's figure over 96 handoffs, a 0.69× ratio that the earlier 64-handoff run also gave; the history question) matches the assessment's §1 and §7 and the study's §10.5, which holds the handoff counts and token totals.

### 1.2 Disagreements, with reasons

1. **The first-use contract.** The second opinion freezes a *GBG* contract (task status, dependencies, acceptance facts, contradictory updates, nested dependencies, distracting text) as the pilot's schema. I disagree for the pilot: that schema does not exist in any codec yet, free text is not in the compact codes' design at all and nesting (the codec's `if` records) was never trained or implemented in the public codec, and a new schema breaks the only paired evidence the project has (three-seed byte-model results and the v3 handoff demo on the seven-field record). The pilot's question is narrower and answerable in days: *does a pretrained model read the compact codes as well as JSON and English, and what does that cost per correct answer?* The GBG schema is the right next contract **after** that answer, and the package's generator and grader are keyed by task and arm, so a second schema is an added generator and renderings plus a new answer shape in the grader and the shared module (and a Sylang encoding for that schema, which no codec has yet), not a rewrite of the training or evaluation code. The second task the pilot adds (lookup of one record's relation and polarity by its identifier pair) is chosen because it exercises reading one record by its identifiers rather than filtering the list (identifier handling is where the byte model failed first, though the lookup answer itself copies no identifier), and because it costs no extra cases or cells: the same cases carry both tasks (each case yields two examples, so training passes and evaluation items double, which stage A's projection counts).
2. **How much of M to change at once.** The second opinion asks for several reversible M improvements, tested individually. The assessment measured the candidates under the Qwen 3 tokenizer (§2.1): the dictionary *costs* 14–29% on identifiers of 2–5 characters and pays only on 12–20-character labels; macro codes save 1%; spaces instead of tabs save 6% of record tokens at every distribution; grouping by subject saves 3% on unique subjects and 20% at K = 16 when half the records reuse a subject (29% when four in five do). Of the ideas that pay on the pilot's data, only grouping changes what the model must learn (a different line grammar); the dictionary is excluded by its measured cost on short labels, and the space separator, which the assessment had scheduled as a GPU factor, is dropped from the cell count as a tokenisation-only change. So the improved-M candidate is grouping alone, on data with repeated subjects, and the pilot reports what it adds over the current compact format. Spaces and the dictionary are tokenizer-arithmetic results: they go into the codec as options when the deployment path needs them, each still subject to a short accuracy check at that time, not into this pilot's cell count.
3. **The gate.** The second opinion's gate is, in short, improved M no more than two percentage points below the best of the other three and at least a 15% measured cost or latency improvement, with results called inconclusive when intervals are too wide. The pilot makes that rule precise by placing the bound on the interval's lower end rather than on the point estimate: an estimate within two points can sit inside an interval that also contains a ten-point loss. The pilot's rule (section 3.4) is non-inferiority with δ = 3 on a 90% cluster-bootstrap interval, an *inconclusive* verdict when the interval straddles −δ, and the 15% whole-request cost criterion under both cache conventions. The assessment's earlier wording ("tied") is withdrawn.
4. **Dataset size.** The second opinion's example range of 5,000–20,000 training cases (which it says to reduce after profiling) is more than the pilot's required cells use; the package uses nested prefixes of 500, 2,000 and 8,000 cases (two examples per case): the required cells run at 2,000, the curve is read from three points on the `english` and `sylang2` arms when the stage-A projection allows the optional 500- and 8,000-case cells (`STAGE_B_CURVES=1`), and stage C stays at 2,000 unless that curve rises by more than 3 points between 2,000 and 8,000 (§3.3), in which case the stage-C configs are regenerated at 8,000 before it starts.
5. **QLoRA.** Expected to be unnecessary for a 0.6B or 1.7B model on a 24–48 GB card (the assessment estimates bf16 LoRA at 1,024 tokens and micro-batch 4 at 5–8 GB and 9–14 GB; the package's batch of 16 is what stage A measures, and a 1.7B run on a 24 GB card is the case to watch), and quantisation would add a second departure from the bf16 deployment setting to every arm. Plain LoRA in bf16, verified by stage A on the real card.
6. **Provider and prices.** The second opinion quotes Runpod's RTX 4090 at US$0.89 (the Secure Cloud price; Community is US$0.34 and closed to new hosts, so its stock is a daily matter) and treats Runpod/Vast as the venue. Section 4 re-checks eight options against today's official pages (Vast's price and Colab's compute-unit rate come from third-party trackers, as the table marks); the pilot's 16 budgeted GPU-hours cost US$0 out of pocket on two providers' free credits and under US$7 on the cheapest paid plain-VM option (Thunder Compute, US$6.60; Salad is cheaper in dollars but needs checkpoint-recovery plumbing).
7. **Scope of "M".** The second opinion's fused forms and custom vocabulary are a separately costed later ablation in both plans (its §4 and §9; the assessment's §2.2 and stage 3); its broader semantic mappings belong to its improved-M candidate and a separate expanded-coverage suite, which this pilot does not include. The pilot tests the compact-codes family only. No disagreement, stated here so that no "M gain" is read into the pilot's result.

### 1.3 Where the assessment was wrong, corrected here

The assessment's §3–§4 proposed 54 runs before any profile, a single task, "tied" as a verdict, runtime figures derived from anchors on other GPUs, and a cost estimate (US$15–35) without a measured cycle. All five are replaced by sections 2–3.

## 3. The revised pilot

### 3.1 Fixed elements (the contract)

The full text is `experiments/pretrained_pilot/contract.md`; the file formats are in `interfaces.md`. In brief: the study's seven-field records with identifiers of 2–5 characters from the v3 hash split; subject reuse 0.5 and object reuse 0.2 with records of one subject adjacent; K 1..12 trained, 13..16 held out; two feature pairs held out; two tasks (*select*: the negated records' pairs in order; *lookup*: relation and polarity of one named pair) with four trained and two held-out wordings each; four arms (`english`, `json`, `sylang2`, `sylang2g` = grouped by subject); a per-arm legend of 100–130 Qwen 3 tokens, matched within 15 tokens; splits by case hash, dev and test shared across seeds; train prefixes 500 / 2,000 / 8,000 cases per seed, dev 400 cases, test 1,000 cases in four panels (iid 480, held-out wording 160, held-out pair 160, K 13..16 200); strict grader; one retry with the format reminded, both requests counted; greedy, non-thinking decoding.

**Model.** `Qwen/Qwen3-0.6B` (Apache-2.0, the tokenizer family of every count in this project), LoRA rank 16 on all linear projections, bf16, 2 epochs, AdamW, warm-up then cosine decay, batch 16, sequence ≤ 1,024 tokens, dev-selected epoch (dev accuracy by generation on 200 dev examples). Memory: the CPU smoke in float32 needed more than 14 GB at batch 4 (the 151,936-wide logits and their gradient dominate); in bf16 at batch 16 the estimate for the longest batches is 13–15 GB, inside an L4's 24 GB but measured by stage A; if a cell runs out of memory, `configs/gen_configs.py --batch-size 8 --grad-accum 2` keeps the effective batch and halves the peak. `Qwen/Qwen3-1.7B` only under the trigger in §3.5.

### 3.2 Stages, cells and what each is for

|---|---|---|---|---|

### 3.3 Expansion criteria (B → C, C → 1.7B) and stop rules

B → C proceeds only if all hold: (1) every B cell completed inside 1.5× its projected time and the measured spend is at most 35% of the ceiling; (2) the pipeline is sane: the zero-shot `english` baseline returns the right answer shape on most items (format compliance after the fence tolerance of the 2026-10-22 amendment; its accuracy is reported but not required, since an untrained 0.6B model need not do the task, and the real-weights CPU smoke showed it listing every record rather than the negated ones) and the trained `english` arm reaches ≥ 90% on the iid panel at 2,000 cases, or its training loss is still falling at the end of epoch 2 (then C runs at 8,000 cases if the projection allows, else with 3 epochs; `configs/gen_configs.py --stage-c-train-size 8000` or `--stage-c-epochs 3` regenerates the stage-C configs and plan file); (3) no grader or data defect was found (the `--check` pass and the invalid-rate review). If the curve for `english` or `sylang2` rises by more than 3 points between 2,000 and 8,000 cases, stage C uses 8,000. If B shows every arm at or above 97% on every panel, the task is at ceiling for a pretrained model: C still runs (the cost and latency comparison stands on its own) and the next data family is the harder one (K to 32, long labels), reported as such.

Stop rules: the ceiling is reached before C can be read (stop, report what was measured, no top-up); B shows a pipeline defect that a second B run does not cure (stop and report); the owner withdraws the approval.

### 3.4 Decision rules (pre-registered; applied at stage C only)

For each contrast, on each test panel and task, paired per item within each seed: a 90% cluster-bootstrap interval of the mean accuracy difference in points (seeds resampled, then items within seeds; 2,000 resamples; bootstrap seed 0), with the per-item-only interval beside it. With δ = 3: **non-inferior** if the lower bound is above −3; **inferior** if the upper bound is below −3; **superior** if the lower bound is above +3; **inconclusive** otherwise. An inconclusive result at three seeds may be followed, once, by two more seeds on the two arms in the contrast if the ceiling allows; after that it stands as reported. Stage B's single seed gives no verdict.

The contrasts, in order of importance for the owner's priority:

1. `sylang2g − sylang2` (what the improved-M candidate adds over the current compact format): kept as the candidate only if non-inferior on every panel and cheaper by the measured margin on the pilot distribution (the §2.1 arithmetic predicts −20% record tokens at K = 16).
2. `sylang2 − json` and `sylang2 − english` (the format question): the project's machine-efficiency direction is alive if the codes are non-inferior to both on the iid panel and inferior on none of the held-out panels.
3. The cost question, for every arm beside `json` and `english`: cost per correct answer (GPU time at the quoted price, all requests and retries included) and the whole-request token totals under the cached and the uncached legend conventions (the package derives dollars from GPU time; the token totals are the cache-dependent part), with whole-request latency batched and single. The second opinion's 15% threshold is adopted as the *engineering* bar for the next stage: a format that is non-inferior is reported as "not worth a format change at this K" unless it saves at least 15% of whole-request tokens under both conventions, or 15% of whole-request latency, against the stronger of `json` and `english`.
4. The `bare` answer format on `english` and `sylang2` (stage C): its accuracy, token, latency and cost tables are reported beside the JSON-format cells (the analysis groups by answer format and computes no paired bare − json interval); nothing is adopted from it.

### 3.5 Reading a failure (so that a 0.6B result does not end the direction by accident)

| observation | reading | next step |
|---|---|---|
| every trained arm fails and the zero-shot `english` baseline is also at chance on *select* | suspect the pipeline (legend, chat template, decoding, grader) before the model | fix, re-run one B cell, no new money beyond stage B's budget |
| every arm below 90% at the largest size run (2,000 cases in the default plan; 8,000 in the full one) with training loss still falling | undertrained | 3 epochs or 8,000 cases within C's budget (`configs/gen_configs.py --stage-c-epochs 3` or `--stage-c-train-size 8000` regenerates the configs and plan file), then re-read |
| `english` and `json` learn, the codes do not, and the gap **shrinks** with data | a capacity/data question | the 1.7B extension on `sylang2` and `json` |
| `english` and `json` learn, the codes do not, and the gap does **not** shrink | a format result for this model size | reported as such; under the assessment's §5.5 the pretrained line stops and the niche is from-scratch or tiny models and custom-tokenizer models; re-asking the question at a larger model is a new owner option this revision adds |
| one arm flat or below the others at every size while at least one arm learns | that arm's format failed | reported; no rescue |

### 3.6 What a success would and would not establish

A success (contrasts 1–2 non-inferior on three seeds, the cost ratio under both conventions) establishes: that a 0.6B pretrained model fine-tuned on identical cases reads the header-free compact codes within δ = 3 points of compact JSON and controlled English (non-inferior) on in-distribution cases, is not inferior to them on unseen identifiers, unseen wordings, unseen feature pairs and unseen record counts, and reads the grouped variant within δ of the ungrouped codes; the measured whole-request token, latency and cost differences for this schema, these two tasks and this tokenizer; and whether grouping by subject is worth its grammar change on handoff-like data.

It would **not** establish: human readability (deferred by the owner); results on real GBG workflows, nested dependencies or free text; other model families, larger models or hosted models; custom-token vocabularies; record counts beyond 16; robustness to adversarial or quoted text inside records; production savings, which depend on the deployment's cache behaviour and request mix. Each of these is a later stage or a separate decision.

#### 6.1.1 Code-review findings

Thirty findings were raised, six were refuted by the second reader, twenty-four were confirmed (seven major, seventeen minor, none blocking) and all twenty-four were fixed before the package was re-tested. The seven major ones, each of which would have changed a number, a verdict or a kept file:

1. A kill between writing an epoch checkpoint and refreshing `best/` left the stale adapter under the newer `selected_epoch`; `--resume` now re-derives `best/` from the checkpoint it names.
2. The evaluator's "conversion-in" time was prompt assembly, not the codec; the generator now records each example's rendering wall-clock (`render_s`) and the evaluator reports it as the codec time, with tokenisation and parsing timed separately.
3. The analysis keyed results by the config's `model` field, which is null for every stage cell, so results from different weights would have merged; the key is now the weights' directory name recorded by the evaluator.
4. The analysis issued pre-registered verdicts at two shared seeds; the rule now requires three (fewer is "exploratory: no decision"), and stage C refuses to run without stage B's seed-0 results unless told to fill or to proceed.
5. The stage scripts packaged the ledger before writing the `stop` line, so the tarball never carried it; the order is reversed.
6. An SSH drop (SIGHUP) made the scripts write "exit 0" and package results while training kept running and billing; the scripts now trap HUP/INT/TERM, kill the child process group, note the interruption in the ledger and exit non-zero.
7. The GPU setup script would have installed a multi-gigabyte torch before failing on an image with Python below 3.12 (the numpy pin); it now checks the interpreter first.

The minor ones (fixed): the pair-panel lookup query now names the forced held-out record (otherwise 57% of those queries would have hit trained pairs and diluted the panel); the grouped arm's legend is now token-identical to the ungrouped arm's (it was 6 tokens longer, a fixed cost against the candidate); a frozen dataset version is never overwritten without `--force`; the manifest records a digest of the packet modules that render English; the profiler no longer stores the upload command or its output (a credential risk) and profiles the longest arm so the projection is conservative, writes its measurement before projecting, validates the plan files before any GPU time, counts both model loads, and prints the cells its projection predicts to exceed their timeout; the evaluator warms up before timing, samples single-request latency from both tasks, and decodes with the same rule as dev selection; resumed runs no longer duplicate log lines; the stage-A ceiling check counts the session's own elapsed spend; an upload failure can be recorded in the ledger; the upload command's arguments are not echoed into logs; the secondary (before-retry) table carries no verdict column.
