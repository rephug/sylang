# What the existing select and lookup tasks can measure

Generated by `analyze_existing.py` from the frozen pilot v1 dev (400) and test (1,000) cases, regenerated with the pilot's own generator and verified against `data_v1_manifest.json` (dev hash match: True, test hash match: True).

These are properties of the tasks and the data, not of any model. A task whose answer does not depend on a feature cannot show that a model reads that feature, and it cannot show that the model does not.

## 1. Which features the answers depend on

Every record of every test case, every feature, every other value of that feature: the share of these single-field edits that change the answer (the pilot's own `select_answers` / `lookup_answers`).

| feature | single-field edits | select answer changes | lookup answer changes (edits of the queried record) |
|---|---|---|---|
| relation | 15,978 | 0.0% | 100.0% |
| polarity | 7,989 | 100.0% | 100.0% |
| tense | 15,978 | 0.0% | 0.0% |
| aspect | 15,978 | 0.0% | 0.0% |
| evidence | 23,967 | 0.0% | 0.0% |

So *select* depends on polarity, the subject and object identifiers and record order only; *lookup* on relation, polarity and the binding of the two named identifiers to one record. Neither answer depends on tense, aspect or evidence in any case: those three features are carried by every rendering but never tested. In particular the held-out-pair panel, whose queried record carries (contain, future) or (help, completed), asks only for relation and polarity: it can show whether an unseen co-occurrence in the input disturbs reading relation and polarity, not whether the model composes tense or aspect with relation.

## 2. One character per record solves both tasks

In the codes a record's polarity is the case of the first letter of the middle field and its relation is that letter. Solvers that read only that character (or only the json keys `r` and `neg`) and never a tense, aspect or evidence letter, scored with the pilot's grader:

| arm | panel | n | select | lookup |
|---|---|---|---|---|
| sylang2 | iid | 480 | 100.0% | 100.0% |
| sylang2 | long | 200 | 100.0% | 100.0% |
| sylang2 | pair | 160 | 100.0% | 100.0% |
| sylang2 | wording | 160 | 100.0% | 100.0% |
| sylang2g | iid | 480 | 100.0% | 100.0% |
| sylang2g | long | 200 | 100.0% | 100.0% |
| sylang2g | pair | 160 | 100.0% | 100.0% |
| sylang2g | wording | 160 | 100.0% | 100.0% |

Perfect scores here mean a perfect model score is *compatible* with reading one character per record. It does not mean a model uses that shortcut.

## 3. Lookup binding: is the second identifier needed?

| panel | n | subject alone is unique | object alone is unique | one identifier suffices | first record with the subject gives the right answer | first record with the object gives the right answer |
|---|---|---|---|---|---|---|
| iid | 480 | 40.4% | 85.2% | 89.6% | 66.7% | 92.7% |
| wording | 160 | 41.2% | 80.0% | 88.1% | 70.0% | 90.6% |
| pair | 160 | 35.0% | 90.0% | 93.8% | 66.9% | 93.8% |
| long | 200 | 25.5% | 78.5% | 84.0% | 63.5% | 91.0% |

With objects mostly unique (object reuse 0.2), the object identifier alone finds the queried record in most cases, so lookup accuracy cannot separate binding both identifiers from matching one.

On the pair panel the queried relation is always contain or help (the held-out pairs fix it), so a solver that never answers "see" is favoured there relative to iid.

## 5. The existing counterfactual probes

The pilot v1 has no counterfactual panel (its panels are iid, held-out wording, held-out pair, K 13-16). The copy-probe study has several: `copy_probe/language.py` builds `reorder` (records permuted), `swap` (`swap_roles`: subject and object exchanged in every record), `flip` (`flip_one`: one polarity flipped) and `similar` / `similar_control` (a positive partner whose identifier differs from a negative record's in one character, against a fresh-identifier control); `copy_probe/train.py` feeds `probes.counterfactual_probe` a `swap` pair and a `replace` pair (one answer identifier renamed) and measures how the first answer byte's distribution moves. All of them act on the select task, so they probe record order, roles, polarity and identifier copying. None edits tense, aspect, evidence or relation; the only edit that must leave the answer set unchanged is `reorder`, and there the answer's order changes; `replace` renames a single identifier and scores the first byte, not a whole answer under a consistent renaming.

## What follows

Select and lookup measure identifier copying, polarity detection, relation reading and (weakly) pair binding. They cannot measure reading tense, aspect or evidence, combining features, or binding entities across records. `experiments/compositional_diagnostics` adds questions that need exactly those, with matched controls.
